## 한눈에

1. 작업 시작 때 열린 `Design Sync` 이슈를 먼저 본다. `Design: 디자인 시스템` 이슈가 화면 이슈보다 먼저다.
2. 화면의 근거를 판정한다 — GUI 화면 파일에 **Ready for dev**가 붙은 노드가 있으면 GUI, 없으면 와이어프레임(단순 와이어 수준).
3. 구현 전에 Figma 노드 → DS 컴포넌트 매핑 표를 만든다. **커스텀 구현은 최대한 지양한다.** 디자인 시스템과 `src/ui` 컴포넌트를 쓴다.
4. Figma가 커스텀으로 그렸지만 DS로 되는 것은 DS로 구현하고, 코드 주석(`FIGMA-CUSTOM:`) + Figma 코멘트를 남긴다.
5. GUI 화면은 QA 캡처를 Figma 프레임 스크린샷과 나란히 비교해 끝낸다.
6. `gui-screens.md` §0 상태를 갱신하고, 반영한 이슈는 PR 본문 `Closes #n`으로만 닫는다.

## 2. 근거 판정

화면 하나(라우트 하나, 그 안의 상태·폭)를 구현하기 전에 정한다.

1. **그 화면의 GUI 노드에 Ready for dev가 있나** — REST 파일 JSON의 노드 `devStatus.type === "READY_FOR_DEV"`. Ready 노드의 자식은 모두 근거에 들어간다(자식에는 `devStatus`가 따로 없다). 확인 방법은 스킬 ②(`figma_nodes.py ready`).
2. **있으면 GUI가 근거**다. 그 화면의 Ready 노드 전부(모바일·PC 폭, 상태별 프레임)를 읽는다.
   - Ready 노드에 없는 상태·폭(예: 기본 정보 1280 PC, ⋮ 메뉴를 연 상태)은 같은 화면의 Ready 노드 + 반응형 스펙(`gui-screens.md` §3) + DS 컴포넌트로 채운다. 이렇게 정한 것은 근거 없이 정한 것이므로 `figma-dev-sync`로 디자이너에게 남긴다(§8).
3. **없으면 와이어프레임이 근거**다(§3). Ready 표시가 없는 GUI 프레임은 작업 중이라 모양을 가져오지 않는다. 문구·구성이 와이어와 다르면 와이어를 따르고 차이만 적어 둔다.
4. 판정 결과(근거 노드, Ready 여부)를 구현 전에 `gui-screens.md` §0 그 화면 줄에 적는다.

- 노드 id는 디자이너가 프레임을 다시 만들면 바뀐다. 근거는 **노드 id + 프레임 이름** 둘 다로 적고, id로 못 찾으면 이름으로 다시 찾는다.
- 한 번 Ready였던 노드가 Ready가 아니게 됐거나 지워졌으면 그 화면 작업을 멈추고 사용자에게 알린다(디자이너가 다시 손대는 중일 수 있다).
- Figma의 **동작 변경**(기능·API 흐름이 바뀌는 것)은 GUI가 Ready여도 계획을 바로 바꾸지 않는다 — `plan.md` §0 "디자인 근거의 우선순위"대로 `design-requests.md`에 질문으로 올린다. UI만 바뀌고 API·흐름이 같은 것은 V 범위로 반영한다.

## 3. 와이어 수준 구현 — 부채로 남긴다

Ready for dev가 없는 화면은 와이어프레임을 근거로 **단순 와이어 수준**으로 만든다.

- 와이어에서 가져오는 것: 무엇이 어떤 순서로 있나(구조), 문구, 동작(누르면 어디로, 어떤 상태가 있나).
- 모양은 **DS 토큰·컴포넌트만** 쓴다. 모양을 지어내지 않는다 — 와이어의 회색 상자·임시 크기를 그대로 옮기지 않고, 새 색 강조·그림자·장식·일러스트를 더하지 않는다. 배치는 프리미티브(`Flex`·`Spacing`·`Txt`·`Divider`·`Container`)로 단순하게.
- `src/ui`에 없는 컴포넌트가 필요하면 화면 안에서 짓지 않는다. 프리미티브만으로 기능이 되게 두고, 반복되면 `design-system.md` §3 "없는 컴포넌트"에 적는다.
- 상태표에 **`와이어로 구현됨`** 으로 남긴다. 나중에 그 화면의 `Design: Ready for dev` 이슈가 오면 GUI로 다시 입힌다(§4). 와이어로 만든 화면은 갚아야 할 부채다.

## 4. 디자인 이슈(`Design Sync`)

### 라벨

| 묶음 | 라벨 |
|---|---|
| 전체 | `Design Sync` |
| 유형 | `Design: 수정` · `Design: 신규 화면` · `Design: Ready for dev` · `Design: 삭제` · `Design: 디자인 시스템` |
| 파일 | `Figma: GUI` · `Figma: 와이어프레임` · `Figma: 디자인 시스템` |
| 테스트 | `Test: figma-plugin` — 플러그인 시험용. 반영 대상이 아니다 |

이슈 본문에는 프레임 표(이름 링크·노드·Dev Mode)와 숨긴 마커 `<!-- figma-node:<fileKey>/<nodeId> -->`가 프레임마다 있다. 디자이너가 같은 프레임에 이어 쓰면 **댓글**로 붙는다 — 본문과 댓글을 모두 읽는다(형식은 `tools/figma-plugin/README.md`).

### 처리 순서

1. **작업 시작 때 먼저 본다**:
   ```bash
   gh issue list --label "Design Sync" --state open --search '-label:"Test: figma-plugin"' --limit 100
   ```
2. **`Design: 디자인 시스템` 이슈를 화면 이슈보다 먼저** 반영한다 — 토큰·`src/ui` 컴포넌트·스토리를 고치고 `design-system.md`를 갱신한다. 화면이 그 위에 선다.
3. 이번에 만지는 화면에 걸린 이슈(마커의 노드가 그 화면의 근거 노드)는 같은 작업에서 같이 반영한다.
4. 유형별:

   | 유형 | 반영 |
   |---|---|
   | `Design: 수정` | 그 노드를 다시 읽고(스크린샷 + `map`) 바뀐 곳만 고친다. 상태가 `GUI 구현됨`이면 그대로 둔다 |
   | `Design: 신규 화면` | 라우트·Phase를 정하고 `gui-screens.md` §1·§2와 §0에 줄을 더한다. Ready가 아니면 아직 근거가 아니다 — 목록에만 올리고 이슈는 열어 둔다 |
   | `Design: Ready for dev` | 근거가 GUI로 바뀐다. `와이어로 구현됨`·`미구현` 화면을 GUI로 구현(다시 입힘)하고 상태를 `GUI 구현됨`으로 |
   | `Design: 삭제` | 지우기 전에 보낸 이슈다. 그 노드가 근거인 화면·컴포넌트를 확인하고, 화면이 없어지는 것이면(계획이 바뀌는 것) 사용자에게 묻는다 |
   | `Design: 디자인 시스템` | 위 2 |

5. **PR을 올리기 전에 한 번 더** 그 화면의 이슈를 확인한다(작업 중에 새 이슈나 댓글이 왔을 수 있다). 새로 온 것은 같은 PR에 반영하거나, 반영하지 못하면 PR 본문에 적는다.

### 닫는 규칙

- 디자인 이슈는 **반영 PR 본문의 `Closes #n`으로만** 닫는다. 손으로 닫지 않는다.
- 일부만 반영했으면 `Closes`를 쓰지 않고 `Refs #n`으로 걸고, 남은 것을 PR 본문과 이슈 댓글에 적는다.
- 반영하지 않기로 한 이슈(동작 변경이라 질문으로 넘긴 것 등)도 손으로 닫지 않는다 — 이슈 댓글에 이유와 `design-requests.md` 질문 번호를 남기고 사용자에게 알린다.

## 5. 구현 원칙 — 커스텀 지양

사용자 결정(2026-10-31), 그대로 옮긴다:

- **커스텀 구현을 최대한 지양한다. 디자인 시스템과 컴포넌트(`src/ui`)를 쓴다.**
- 커스텀 구현은 **Figma에서도 직접(디자인 시스템 밖으로) 디자인된 부분에만** 허용한다.
- Figma에서는 커스텀으로 그려져 있지만 **디자인 시스템 컴포넌트로 구현할 수 있는 부분**은 DS 컴포넌트로 구현하고, (a) **코드에 주석**으로 남기고, (b) **Figma 해당 노드에 코멘트**를 단다.

### 판단 표

노드마다(스킬 ③ 매핑 표) 정한다. "DS 인스턴스"는 `INSTANCE`이고 메인 컴포넌트(또는 그 세트)가 디자인 시스템 파일 `0QD9tGSt8ZciDqe7ol2gYH`의 공개 컴포넌트인 것이다(판정은 스킬 ③).

| Figma 노드 | 코드 | 주석 | Figma 코멘트 |
|---|---|---|---|
| **DS 인스턴스** | 대응하는 `src/ui` 컴포넌트. 변형(variant)은 props로. `src/ui`에 아직 없으면 화면에서 짓지 않고 `src/ui`에 먼저 만든다(`design-system.md` §4, 스토리 포함) | 없음 | 없음 |
| **커스텀인데 DS로 가능** — 직접 그렸거나 로컬·외부 컴포넌트지만 같은 역할의 DS 컴포넌트가 있고, 차이가 변형·토큰 범위 안 | DS 컴포넌트 | `FIGMA-CUSTOM:` → DS(§6) | 단다(§7) |
| **커스텀이고 DS로 불가** — 같은 역할의 DS 컴포넌트가 없거나 구조가 다르다 | `Foo.css.ts` + 토큰만(리터럴 색·간격·모서리 금지). 반복되면(두 화면 이상) DS 후보로 `design-system.md` §3 "없는 컴포넌트"에 올린다 | `FIGMA-CUSTOM:` → 커스텀(§6) | 없음 |

- **"DS로 가능"의 기준**: 같은 역할(버튼·칩·입력·탭…)이고, Figma와의 차이가 DS 컴포넌트의 변형·토큰으로 표현되거나 화면에서 눈에 띄지 않는 수준(1~2px, 비슷한 회색)이다. 차이가 구조(부품 구성·배치)거나 디자이너가 일부러 다르게 그린 것으로 보이면 불가로 본다. 애매하면 DS로 구현하고 코멘트로 묻는다 — 커스텀 쪽으로 기울지 않는다.
- 외부 라이브러리 인스턴스(iOS `StatusBar`, `lucide/*`, `icon/*`): 상태 바는 구현하지 않는다. 아이콘은 DS `ic`에 같은 것이 있으면 `<Icon>`(이것도 "DS로 가능" 줄), 없으면 `src/ui/icons/README.md` 절차로 DS 아이콘을 더할지 사용자에게 묻는다.
- 글자: 글자 스타일이 걸린 글자는 `<Txt typography>`. 스타일 없이 크기만 준 글자는 가장 가까운 타이포 토큰으로(`design-system.md` §4 "토큰만 쓴다"의 하드코딩 표와 같은 규칙).
- 정적 에셋(일러스트·로고)은 **정확한 것만** 쓴다 — `src/ui/illustrations`·`src/ui/brand`에 같은 것이 있을 때만 그것을, 없으면 Figma 원본을 `design-system.md` §4-1 절차로 들인다. 비슷한 다른 그림으로 바꾸거나 다시 그리지 않는다. 서버가 주는 이미지(포스터·프로필)는 데이터로 둔다.

## 6. 코드 주석 형식

grep으로 모두 찾을 수 있게 접두어 하나로 고정한다: **`FIGMA-CUSTOM:`**

```
FIGMA-CUSTOM: <무엇>(<file> <node-id> "<Figma 노드 이름>") 커스텀 → DS <컴포넌트>. Figma 코멘트 <YYYY-MM-DD>
FIGMA-CUSTOM: <무엇>(<file> <node-id> "<Figma 노드 이름>") 커스텀 → 커스텀 <파일>.css.ts. DS 후보(design-system §3)
```

- `<무엇>`: 우리 말로 그 부분이 무엇인지(Figma 이름이 `Frame 1707480356`처럼 뜻이 없을 때가 많다). `<file>`: `gui` | `wire` | `ds`. `<Figma 노드 이름>`: Figma에 보이는 이름 그대로 — id가 바뀌면 이걸로 다시 찾는다.
- 줄 하나. JSX 안이면 `{/* FIGMA-CUSTOM: … */}`, 그 밖은 `// FIGMA-CUSTOM: …`. 그 요소 바로 위에 둔다.
- 첫째 형식(→ DS)은 §5 "커스텀인데 DS로 가능", 둘째 형식(→ 커스텀)은 "커스텀이고 DS로 불가"에 쓴다. DS 인스턴스에는 쓰지 않는다.
- 예(형식만 보여 준다 — 노드 id·이름은 자리표시):
  ```tsx
  {/* FIGMA-CUSTOM: 티켓 카드 판매 기간 줄(gui 123:456 "Frame 1707480000") 커스텀 → DS InfoRow. Figma 코멘트 2026-11-03 */}
  // FIGMA-CUSTOM: 티켓 카드 상자(gui 123:789 "Frame 1707480001") 커스텀 → 커스텀 TicketCard.css.ts. DS 후보(design-system §3)
  ```
- 찾기: `rg -n 'FIGMA-CUSTOM:' src`. 디자이너가 DS로 바꾸거나 답하면 주석을 지우거나 고친다.

## 7. Figma 코멘트 형식

"커스텀인데 DS로 가능" 노드에 단다. 수단은 `figma-dev-sync`의 `comment.py`(REST, 토큰 출력 금지):

```bash
python3 .claude/skills/figma-dev-sync/comment.py post gui <node-id> --date <YYYY-MM-DD>-impl --key <화면>-<부분> <<'EOF'
[개발 · DS 컴포넌트로 구현] <무엇>
이 부분은 디자인 시스템 밖에서 직접 그려져 있어, 개발에서는 디자인 시스템 <컴포넌트>(<변형>)로 구현했습니다.
달라지는 점: <눈에 보이는 차이 1~2개, 없으면 "없음">
→ 디자인 시스템 컴포넌트로 바꿔 주시거나, 직접 그린 모양이 꼭 필요하면 답글로 알려 주세요.
EOF
```

- 머리말은 `[개발 · DS 컴포넌트로 구현]`으로 고정한다(`figma-dev-sync` 머리말 `[개발 싱크 · …]`과 구별).
- 노드는 그 부분을 가장 작게 감싸는 노드(커스텀 상자·프레임)다. 화면 프레임 전체나 페이지(CANVAS)에는 달지 않는다.
- 기록부 키는 `--date <YYYY-MM-DD>-impl`로 쓴다 — `figma-dev-sync`의 같은 날짜 `clear`가 이 코멘트까지 지우지 않게.
- 문장은 디자이너가 읽는 말로. 코드 경로·토큰 이름을 쓰지 않는다. @멘션은 API로 걸리지 않는다.
- 코멘트 날짜를 §6 주석에 적는다.

## 8. 반대 방향 — 개발이 정한 것

디자인 근거 없이 정한 것(Ready 노드에 없는 상태·폭을 채운 것, Figma와 일부러 다르게 한 것, 와이어 화면에서 정한 배치)은 `implementation-log.md` 그 Phase 절의 "결정"에 적고, Phase를 마칠 때 스킬 `figma-dev-sync`로 GUI 파일 "개발 싱크용" 페이지에 리포트 + 코멘트로 남긴다. §7 코멘트(DS로 바꾼 것)와는 따로다 — 그쪽은 구현하면서 바로 단다.

## 10. 상태표

`gui-screens.md` §0이 화면별 상태의 정본이다. 상태는 셋:

| 상태 | 뜻 |
|---|---|
| `GUI 구현됨` | Ready 노드를 근거로 구현하고 §9 GUI 기준을 통과했다 |
| `와이어로 구현됨` | 와이어를 근거로 구현했다. Ready가 오면 GUI로 다시 입힌다(부채) |
| `미구현` | V를 아직 하지 않았다(L만 있는 최소 마크업 포함) |

줄마다 근거 노드(id + 프레임 이름), Ready 여부, 걸린 열린 이슈를 같이 적는다. 상태를 바꾼 PR이 같은 줄을 고친다. Ready 노드 목록이 바뀌었는지는 작업 시작 때 `figma_nodes.py ready`로 확인해 §0 머리의 기준 시각을 갱신한다.
