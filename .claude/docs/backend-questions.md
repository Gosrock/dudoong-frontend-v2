### B16. 동의 강제 날짜

- 동의 강제(env `AGREEMENT_ENFORCE`, 기본 false)를 켜는 날짜. **2026-11-01 답(#905 §1-1)**: 운영 · 스테이징은 SSM env로 **따로** 켠다(지금 둘 다 꺼짐). **v2만 기록 모드로 두는 길은 만들지 않는다** — 동의는 법적으로 받아야 하는 값이라 v2는 컷오버 전에 동의 칸 4개를 반드시 갖춘다. 운영 강제는 v1 Front #384 배포 뒤 켜고, 켜기 전에 날짜를 Backend #898에 남긴다. 칸을 켠 v2 이미지가 준비되면 #905에 알리면 스테이징만 `AGREEMENT_ENFORCE=true`로 바꿔 준다(런북 §4 리허설). **남은 것**: 날짜(#898).

### B23~B27. 스테이징 QA 제안 #93(2026-11-01) — **답 받음 · 닫음**(Backend #914, 2026-11-02)

이슈 [#93](https://github.com/Gosrock/dudoong-frontend-v2/issues/93) 중 서버 계약이나 기획이 바뀌어야 하는 것 — Gosrock/DuDoong-Backend#914로 전달했고 백엔드가 답하고 닫았다. 서버 변경은 **Api 2.5.6 — 스테이징에만**(Gosrock/DuDoong-Deploy#100, 2026-11-02 00:25 KST), 운영은 2.5.3 그대로이고 컷오버 때 같이 올린다(cutover-runbook). 그래서 새 응답 필드는 zod에서 optional, 새 API·헤더는 스테이징 · 컷오버 기준이다. 반영 PR: `backend-914-sync`.

- **주문 멱등 키(#914 1절 — #923)** — `POST /me/orders`에 선택 헤더 `Idempotency-Key`. 같은 사용자·티켓·키면 24시간 동안 시간·본문과 상관없이 앞 주문(거절·취소 포함). **반영**: 주문 시도마다 새 키(`crypto.randomUUID()`), 응답 없음 · 5xx(`Redisson_500_1` 포함) · `Order_400_26`이면 키를 남겨 [다시 시도]가 같은 키로 보낸다(api-contract §1 "메서드 의미"). #94의 30초 타임아웃 + "주문내역 확인" 안내는 [다시 시도] · [주문내역 확인] 두 버튼으로 합쳤다(`Order_400_26`도 이제 주문내역으로 보내지 않고 같은 안내).
- **B23. 주문을 입금 전에 먼저 만들기 — 닫음**. 답: 서버 변경 없이 순서만(주문은 만드는 순간 승인 대기 + 재고 잡힘). 입금 기한 · 자동 취소 · "입금했어요" 알림은 출시 뒤 별도. **사용자 결정(2026-11-02)**: [결제하기] → 주문 확인 [주문 완료하기] → O-1 → 주문 완료 화면에 입금자명 · 계좌(복사) · 입금할 금액 · [토스 앱에서 송금하기] → 은행 앱. 주문상세(O-3)에서도 계좌와 (승인 대기 + 토스 송금이면) 토스 버튼을 다시 본다. 두둥 입금 전 확인(legal-copy A-6)은 주문 확인 모달에 그대로 — 입금보다 앞이라 "입금 전 확인"이 맞고 문구는 바꾸지 않았다. 디자인은 design-requests Q97.
- **B24. 입금자명 — 닫음(닉네임 고정 유지)**. 답: 서버는 자유 입력(1~20자)이라 고칠 수 있게 해도 된다(예매자 관리 · 엑셀 · 검색에 그 값). **사용자 결정(2026-11-02)**: 고정 유지 — "이제 닉네임 변경이 가능하니 닉네임에 맞추도록". 입력칸을 만들지 않고 #105의 "닉네임을 마이페이지에서 바꿔 주세요" 안내를 둔다.
- **B25. 공연 카드 가격 · 매진 — 닫음**(#925). GP-1 · GP-2 항목 `hasTicket` · `minPrice` · `isFree` · `isSoldOut`. 카드 가격 줄은 Q63 기본안(매진 → 무료 → `15,000원~` → 티켓 없음 → 없음). 운영 2.5.3 응답에는 없어 줄이 안 보인다.
- **B26. T-1 묶음 승인형 여부 — 닫음**(#924). `groups[].approvalRequired`가 false면 배지 '발급 완료'(Q74 기본안). 값이 없으면 '승인완료'.
- **B27. 티켓 번호 체크인 — 닫음**(#926). `POST /events/{eventId}/check-ins/by-ticket-no` `{ticketNo}` — 권한 · 공연 상태 · 응답이 PQ-2와 같다. QR 체크인 [호스트가 QR 스캔] 카메라 아래 "티켓 번호로 입장"(디자인 없음 — Q99), 입장 처리 뒤 `ownerName`을 크게. #107의 발급 티켓 [수동 입장 처리](PQ-2 `ticketUuid`)는 그대로.
