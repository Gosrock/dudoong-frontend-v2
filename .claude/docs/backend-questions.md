## 보낼 질문

### B16. 작은 것

- 동의 강제(env `AGREEMENT_ENFORCE`, 기본 false)를 켜는 날짜가 정해지면 미리 알려 달라. 컷오버 체크리스트에 들어간다. (2026-10-31 최종 답: 운영·스테이징 모두 꺼져 있고, 날짜가 정해지면 미리 알려 준다) **2026-10-31 갱신(v1 Front #384, 백엔드 담당 작성)**: 켜는 시점은 "v1 호스트 어드민 카카오 가입에 동의 값을 보내는 수정이 배포된 직후"다 — 날짜는 아직 없지만 v2 출시보다 먼저일 가능성이 크다. 알림 요청은 Backend #898. 새로 물을 것: ① 강제를 켜는 날짜·환경(운영·스테이징을 따로 켤 수 있나 — 같은 `AGREEMENT_ENFORCE` env)을 v2 출시 전에도 미리 알려 달라. v2 스테이징 리허설에서는 강제를 켠 백엔드로 확인하고 싶다(plan P15). ② v2가 동의 칸(디자인 Q42)을 갖추기 전에 강제가 켜지면 v2 가입·주문·두둥티켓 생성이 전부 400이다 — v2 출시(컷오버) 전까지 v2 경로만 기록 모드로 둘 방법이 있나, 아니면 v2는 출시 전에 칸을 반드시 갖춰야 하나.
- (계약 대조 2026-10-31, 참고) 멤버 일괄 추가(PH-7)가 동시 추가로 unique 위반이 나면 `HOST_400_15` 사유에 **요청한 이메일 전부**를 붙인다(`V2AddHostMembersUseCase` `DataIntegrityViolationException` 분기 @fe423ed4) — 실제로 이미 멤버인 이메일만이 아니다. 프론트는 사유의 이메일을 줄에 맞추므로 이 경우 모든 줄에 "이미 멤버"가 붙는다. 가능하면 겹친 이메일만 알려 달라. (`cb53bfaa`에서도 그대로)
- (계약 대조 2026-10-31, 참고) 백엔드 `api/v2/README.md` M-2 설명("유니코드 공백만인 이름은 `V2UserDomainService`가 400 `USER_400_4`")이 #884 뒤 동작과 다르다. 지금은 `@Pattern`(`\p{javaWhitespace}`)이 먼저라 공백만인 이름은 400 `BAD_REQUEST`이고, `USER_400_4`는 줄바꿈 금지 공백(U+00A0 등)만인 이름에만 온다. 문서만 맞춰 달라. (`cb53bfaa` README 191행도 그대로 — #887은 다른 두 줄만 고쳤다)
- (계약 대조 2026-10-31, 참고) 호스트·공연·옵션 이름의 `@Pattern(".*\\S.*")`(`V2UpdateHostRequest`·`V2UpdateEventBasicRequest`·`V2TicketOptionRequest` @fe423ed4)은 Java `\S`가 전각 공백(U+3000)을 공백으로 보지 않아 통과시킨다. 호스트는 `V2UpdateHostUseCase`의 `trim()`이 그 공백을 지워 **빈 이름이 저장된다**(공연·옵션은 패턴만 확인). 프론트는 보내기 전에 `trim()`으로 막는다 — 다른 경로 대비로 `\p{javaWhitespace}`(마이페이지 이름처럼)나 trim 뒤 검사를 제안. (`cb53bfaa`에서도 그대로)
- (이슈 #8 sitemap, 2026-10-31) GP-2(`GET /api/v2/events`) 항목에 `hostId`와 `updatedAt`을 더해 줄 수 있나? 둘 다 `Event` 엔티티에 이미 있다(`hostId`, `BaseTimeEntity.updatedAt` @`78b1b6e7`). 지금 `V2EventListItemResponse`에는 `hostName`만 있고 공개 호스트 목록 API도 없어서, 프론트 `sitemap.xml`이 호스트 홈 주소를 모으려고 종료 전 공연마다 GP-3을 한 번씩 부른다. 수정일이 없어 `lastModified`도 비워 둔다. 더해 주면 GP-3 호출이 사라지고 `lastModified`를 채운다(`src/api/server/sitemap-source.ts`).

### B18. 두둥티켓 승인 대기 주문 셀프 취소 — 약관·안내 개정 문구 대기 — **위험: 서버 동작과 약관 안내가 다름**

- **답(2026-10-31)**: 서버는 바꾸지 않는다 — 관객은 두둥 승인 대기(`PENDING_APPROVE`) 주문을 앱에서 취소할 수 있고, 프론트는 `canCancel`대로 그린다. 약관 제27조③과 안내 문구(legal-copy A-2 ⑤·A-7 ⑤·A-8 ⑤-b)는 백엔드(운영)가 고친다.
- **남은 것**: 개정 약관 제27조③·안내 문구 원문(2026-10-31 최종 답: "따로 드리겠다"). 받으면 legal-copy 해당 행과 `agreementVersion`을 바꾼다. 그 전에 출시하면 안내와 동작이 어긋난다.
- 승인 전 취소의 호스트 메일 제목·본문은 "입금됐다면 환불해 주세요"로 바뀌었다(#887, api-contract §6 취소 절 — 옛 B13).
