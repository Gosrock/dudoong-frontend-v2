## 보낼 질문

### B16. 동의 강제 날짜

- 동의 강제(env `AGREEMENT_ENFORCE`, 기본 false)를 켜는 날짜. **2026-11-01 답(#905 §1-1)**: 운영 · 스테이징은 SSM env로 **따로** 켠다(지금 둘 다 꺼짐). **v2만 기록 모드로 두는 길은 만들지 않는다** — 동의는 법적으로 받아야 하는 값이라 v2는 컷오버 전에 동의 칸 4개를 반드시 갖춘다. 운영 강제는 v1 Front #384 배포 뒤 켜고, 켜기 전에 날짜를 Backend #898에 남긴다. 칸을 켠 v2 이미지가 준비되면 #905에 알리면 스테이징만 `AGREEMENT_ENFORCE=true`로 바꿔 준다(런북 §4 리허설). **남은 것**: 날짜(#898).

### B23~B27. 스테이징 QA 제안 #93(2026-11-01) — 계약에 닿는 것

이슈 [#93](https://github.com/Gosrock/dudoong-frontend-v2/issues/93) 중 서버 계약이나 기획(서버 쪽 기본안)이 바뀌어야 하는 것이다. **백엔드에 전달함 — Gosrock/DuDoong-Backend#914**(2026-11-01, 사용자 지시). 같은 이슈 1절에 주문 생성 멱등 키(`Idempotency-Key` 없음 · 중복 판정 10초 창 — #94)도 넣었다.

- **B23. 주문을 입금 전에 먼저 만들기**(#93 §2 ⭐) — 지금은 체크아웃 [주문 완료하기] → "입금 하셨나요?" 확인 → 그때 주문 생성(PO-1). 은행 앱에 갔다 오면 주문이 없고 재고도 안 잡히며, 입금 뒤 앱이 꺼지면 돈만 보낸 상태가 된다. 제안: 주문(입금 대기)을 먼저 만들고 계좌 · 입금 기한을 보여 준 뒤 "입금했어요"로 호스트에게 알림. 서버에 입금 대기 상태 · 기한 · 기한 지나면 자동 취소(재고 반환)가 필요하다. **답이 없으면**: 지금 흐름 그대로.
- **B24. 입금자명 수정**(#93 §2) — 기획서 기본안 "입금자명 = 닉네임 고정"(위 "지켜보는 것")이라 부모님·친구 계좌로 입금하면 호스트가 맞춰 볼 수 없다. 서버 PO-1은 `depositorName`을 받는다. 체크아웃에서 고칠 수 있게 해도 되나(호스트 예매자 관리 · 엑셀에 그 값이 나오는지)? 화면 라벨 '예매자명' / 안내 '입금자명'이 섞인 것도 같이 정리한다. **답이 없으면**: 닉네임 고정 그대로.
- **B25. 공연 카드에 가격 · 매진 값**(#93 §1 ⭐, design-requests Q63) — GP-1(홈) · GP-2(목록) 항목에 최저 가격(`minPrice`), 무료 여부, 티켓 없음(`hasTicket=false`), 전부 매진 여부를 더해 줄 수 있나? 지금 카드 응답에는 없어 카드마다 GP-5를 부를 수는 없다. **답이 없으면**: 카드에 가격 줄 없음.
- **B26. T-1 묶음에 승인형 여부**(#93 §3, design-requests Q74) — 무료 선착순(즉시 발급) 티켓도 배지가 '승인완료'다. O-3에는 `approvalRequired`가 있지만 T-1 묶음(`V2MyTicketsResponse`)에는 없다. 묶음에 `approvalRequired`(또는 `orderMethod`)를 더해 줄 수 있나? **답이 없으면**: 모두 '승인완료'.
- **B27. 티켓 번호로 직접 체크인**(#93 §5) — 카메라를 못 쓰는 현장에서 티켓 번호(`T1000118`)를 입력해 체크인. 지금 PQ-2는 QR 값(티켓 uuid)만 받는다. 번호로 받는 API(공연 범위 · 권한 같음)를 둘 수 있나? **답이 없으면**: 카메라 · [관객이 QR 스캔](셀프 체크인)만. 카메라 대기 · 권한 안내는 #93 PR에서 넣었다.


### B28~B30. 스테이징 QA #105 · #106 관객(2026-11-02) — 약관 문구 · 환불 기준 · 체크인 회차

이슈 [#105](https://github.com/Gosrock/dudoong-frontend-v2/issues/105) · [#106](https://github.com/Gosrock/dudoong-frontend-v2/issues/106) 관객 쪽 중 약관 근거 문구(운영 확인 없이 바꾸지 않는다 — legal-copy)나 서버 값이 있어야 하는 것이다. 호스팅 쪽 #106은 B31~(병렬 세션). **아직 보내지 않았다** — 관제탑이 다음 백엔드 전달 때 같이 보낸다.

- **B28. v2용 약관 근거 문구 확인(운영)** — legal-copy의 v1 원문 중 v2 화면과 맞지 않는 두 곳. 확정본을 주면 그대로 바꾸고(동의 체크 문구가 아니면 `agreementVersion`은 그대로 — #897 §3), 주지 않으면 원문을 둔다.
  - ① **A-1 공연 상세 중개자 고지**의 "취소·환불 규정은 **'판매정보'**와 이용약관에서 확인할 수 있습니다" — v2 공연 상세에는 '판매정보' 탭이 없다(섹션 제목은 호스트가 정함, 기본 '공연소개'). 제안: "…호스트가 공연 상세에 안내한 환불 기준과 이용약관에서…"(#105 1행).
  - ② **"취소한 뒤 호스트에게 연락해 환불받을 계좌를 알려주세요"**(A-7 ④ · A-8 ④ · A-9 본문 · A-11 토스트 "호스트에게 연락해 환불을 요청해주세요") — v2는 취소할 때 앱에서 계좌를 받아 호스트에게 바로 보인다(O-4 `refundAccount` 필수 · O-5). 취소 시트에 원문 바로 아래 계좌 칸이 있어 "어디에 알리라는지"가 서로 다르다(#105 6행). 약관 제29조③은 "서비스에 입력하거나 호스트에게 알린 때" 둘 다 허용한다. 제안: B18 확정 문구처럼 "취소할 때 입력한 환불 계좌로 호스트가 환불합니다. 환불이 늦어지면 호스트에게 연락해 주세요." **지금**: 원문 그대로 + 계좌 칸 위 비약관 안내 줄("여기에 입력한 계좌는 호스트에게 바로 전달되고…")만 고쳤다.
  - **답이 없으면**: 원문 그대로.
- **B29. 공연별 환불 기준 · 오늘 기준 환불 예상(Backend #870)** — #105 "백엔드 #870 이후" 제안. 구조화된 "두둥티켓 취소·환불 기준" 필드 + 주문 시점 스냅샷이 생기면 티켓 선택 → 체크아웃 → 주문 완료 → 주문상세 → 취소 시트 다섯 곳에 같은 문구, 취소 시트에 "지금 취소하면 OO원 환불"을 보인다. 호스트 입력칸은 티켓 만들기(P12). **지금**: 체크아웃 규정 보기 · 주문상세에 "취소 기한 · 공연 시작 전 까지" + 공연 시작 일시, 호스트 기준은 공연 상세 링크로만. **답이 없으면**: 지금 그대로.
